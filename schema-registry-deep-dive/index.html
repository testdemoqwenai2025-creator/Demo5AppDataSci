Learning Path
Seven primitives, each rooted in ConceptCard 53. Walk through them in order: namespacing (Subject) → policy (Compatibility) → wire format (Avro evolution) → tradeoff (Protobuf vs Avro vs JSON Schema) → versioning (Latest vs URL) → lifecycle (Soft vs Hard delete) → wire format (Schema ID in headers).
1

Subject

ConceptCard #53focus: namespacing

Named schema collection (e.g., 'users-value'). The '-value' / '-key' suffix is convention. Each register call appends a new version.

SubjectVersion(subject) → version n+1

2

Compatibility

ConceptCard #53focus: policy

BACKWARD (default) / FORWARD / FULL / NONE. Per-subject override via PUT /config/{subject}. Transitive = check against ALL versions.

compat(S_n, S_{n+1}) ∈ {BW, FW, FULL, NONE}

3

Avro schema evolution

ConceptCard #53focus: wire format (Kafka default)

Schema-first wire format. Producer + consumer exchange 4-byte schema ID; consumer looks up schema by ID. Default compatibility BACKWARD.

msg = [0xFF, schema_id(4), payload(avro)]

4

Protobuf vs Avro vs JSON Schema

ConceptCard #53focus: wire format tradeoff

Avro = schema-first (Kafka data). Protobuf = tag-numbered (gRPC). JSON Schema = lightweight (REST). Same compatibility math at different layers.

Avro: S_{n+1} ⊇ S_n; Protobuf: tag numbers stable; JSON Schema: weaker types

5

Latest vs URL strategy

ConceptCard #53focus: versioning strategy

Latest = consumer auto-tracks head (risky for shared topics). URL = consumer pins to specific version (safe for cross-team contracts).

GET /subjects/{s}/versions/latest vs /versions/{n}

6

Soft vs hard delete

ConceptCard #53focus: lifecycle

Soft delete = mark version deleted but schema ID still resolvable (consumers don't break). Hard delete = purge from registry (consumers break).

DELETE /subjects/{s} vs /permanent

Schema ID in message headers

ConceptCard #53focus: wire format

Every record carries a 4-byte schema ID prefix (Confluent wire format: 0xFF magic byte + 4-byte big-endian schema ID + Avro payload).

msg = 0x0 | schema_id(4 bytes) | payload

Confluent Schema Registry REST API — the universal contract registry
The REST API that backs every contract registry. POST /subjects/{subject}/versions registers a new schema. POST /compatibility/subjects/{s}/versions/{n} is the CI gate that rejects breaking changes before they ship. PUT /config/{subject} pins per-subject policy. Single-partition compacted Kafka topic '_schemas' is the source of truth.

The REST API is the universal surface — every contract registry (Confluent, Apicurio, AWS Glue Schema Registry) implements the same endpoints. The wire format is JSON: the Avro/Protobuf schema is escaped as a JSON string inside the request body. The response on register is just { id: 42 } — the 4-byte schema ID that gets prepended to every record on the wire. The compatibility endpoint is the CI gate: ship the schema to it before registering, fail the build if it returns is_compatible: false.

Avro schema evolution — 4 versions, 4 compatibility verdicts
Four versions of a User schema demonstrate the BACKWARD/FORWARD/FULL/BREAKING invariants. v1 baseline (3 required fields). v2 add optional 'phone' (FULL — both directions). v3 widen 'id' int→long (BACKWARD only — old int readers can't read long). v4 rename 'email'→'email_address' (BREAKING — no valid transformation, requires blue-green or rollback).

Avro is the canonical wire format for Kafka data platforms because the schema is stored in the registry, not in the message — only a 4-byte ID travels with each record. This means producers and consumers can be on different schema versions and still decode correctly. The compatibility checker is the safety net: it rejects v4 (the rename) before it ships, forcing the team to either blue-green the consumer fleet or roll back to v3. Without this gate, a breaking rename ships silently and consumers start failing on the first read of new data — at 3am.

Compatibility config — global defaults + per-subject overrides
Global default BACKWARD (safe evolution: new readers read old data). Per-subject override to FULL_TRANSITIVE for cross-team shared topics (strictest — both directions, all versions). The Kafka topic '_schemas' is single-partition compacted — the source of truth. mTLS for the REST API in production.

The compatibility policy is the social contract between producers and consumers. BACKWARD (default) says: "producers can ship any change that lets new readers read old data" — i.e., add optional fields, add defaults, widen types. FORWARD (rare) says: "producers can ship any change that lets old readers read new data" — i.e., delete fields, add defaults. FULL (strict) says both. FULL_TRANSITIVE says "both directions, against ALL previous versions, not just the latest" — the strictest, used when you can't coordinate consumer deploys.

Kafka producer with schema ID — Confluent wire format
Every Avro record carries 0x0 (magic byte) + schema_id (4 bytes) + avro_payload. Consumer looks up the schema by ID at read time — no inline schema in the message, no drift between producer and consumer. confluent-kafka-python wraps this; the SerializingProducer auto-registers the schema on first send.

The 4-byte schema ID is the secret to Avro's evolution story. Producers fetch the ID once at startup (cached forever), then prepend it to every record. Consumers fetch the schema by ID on first read (cached forever) — if the producer is on v2 and the consumer is on v1, the consumer still decodes correctly because it gets the writer's schema (v2) by ID, then resolves it against its own reader's schema (v1) using Avro's resolution rules (drop unknown fields, fill defaults). This is why Avro is the wire format for every Kafka data platform: the schema registry decouples producer deploys from consumer deploys.

Schema Registry IS API versioning applied to data — same compatibility invariants govern Kafka Avro, gRPC Protobuf, dbt contracts, and REST API JSON Schema

Connected to: ADR-001 (platform architecture) →

Schema Registry is structurally API versioning applied to data. The same BACKWARD / FORWARD / FULL / BREAKING invariants that govern REST API evolution (gRPC Protobuf, OpenAPI, JSON Schema) govern Avro schema evolution on Kafka, dbt model contracts (since v1.5), and Great Expectations expectations. The pattern is invariant: every change is classified as compatible or breaking; compatible changes ship without coordination; breaking changes require blue-green or rollback. A Kafka Avro consumer, a gRPC client, a dbt model contract, and a REST API caller all benefit from the SAME compatibility checker math — the math says: BACKWARD if S_{n+1} ⊇ S_n (new reader reads old data), FORWARD if S_n ⊇ S_{n+1} (old reader reads new data), FULL if both, BREAKING if no valid transformation f exists. The only difference is the substrate (Kafka topic vs Protobuf descriptor vs dbt YAML vs OpenAPI spec) — the math is universal. Confluent Schema Registry, Apicurio Registry, AWS Glue Schema Registry, gRPC Protobuf, dbt contracts, and OpenAPI specs all converge on the same invariants because they're all solving the same problem: how to evolve a contract without breaking consumers.

Avro vs Protobuf vs JSON Schema — the same tradeoff at different layers

Connected to: ADR-050 (fold-section architecture) →

The three wire formats (Avro, Protobuf, JSON Schema) make the same tradeoff at different layers of the stack. Avro is schema-first + binary: the schema lives in the registry, the message carries only a 4-byte ID, the payload is compact binary. Protobuf is schema-first + tag-numbered: the schema is the .proto file, fields are numbered (adding a new field with a new tag is forward-compatible), the payload is binary but self-describing enough to skip unknown fields. JSON Schema is schema-optional + text: the schema is a validator, the message is human-readable JSON, types are weaker (no native int64, no required-by-default). The tradeoff: Avro is the most compact (best for Kafka data plane) but requires the registry at read time. Protobuf is moderately compact (best for gRPC microservices) and self-describing enough that schema mismatches don't break decoding. JSON Schema is the most flexible (best for REST APIs) but the most verbose. A Kafka engineer using Avro, a microservices engineer using Protobuf, and an API designer using JSON Schema all enforce the same BACKWARD/FORWARD/FULL/BREAKING invariants — only the wire format differs. The choice of wire format is a layer-of-the-stack decision: data plane (Avro), service plane (Protobuf), API plane (JSON Schema). Schema Registry applies the same compatibility math to all three.

Avro schema evolution — 4 versions, 4 compatibility verdicts
Four versions of a User schema demonstrate the BACKWARD/FORWARD/FULL/BREAKING invariants. v1 baseline (3 required fields). v2 add optional 'phone' (FULL — both directions). v3 widen 'id' int→long (BACKWARD only — old int readers can't read long). v4 rename 'email'→'email_address' (BREAKING — no valid transformation, requires blue-green or rollback).

Avro is the canonical wire format for Kafka data platforms because the schema is stored in the registry, not in the message — only a 4-byte ID travels with each record. This means producers and consumers can be on different schema versions and still decode correctly. The compatibility checker is the safety net: it rejects v4 (the rename) before it ships, forcing the team to either blue-green the consumer fleet or roll back to v3. Without this gate, a breaking rename ships silently and consumers start failing on the first read of new data — at 3am.

Compatibility config — global defaults + per-subject overrides
Global default BACKWARD (safe evolution: new readers read old data). Per-subject override to FULL_TRANSITIVE for cross-team shared topics (strictest — both directions, all versions). The Kafka topic '_schemas' is single-partition compacted — the source of truth. mTLS for the REST API in production.

The compatibility policy is the social contract between producers and consumers. BACKWARD (default) says: "producers can ship any change that lets new readers read old data" — i.e., add optional fields, add defaults, widen types. FORWARD (rare) says: "producers can ship any change that lets old readers read new data" — i.e., delete fields, add defaults. FULL (strict) says both. FULL_TRANSITIVE says "both directions, against ALL previous versions, not just the latest" — the strictest, used when you can't coordinate consumer deploys.

Kafka producer with schema ID — Confluent wire format
Every Avro record carries 0x0 (magic byte) + schema_id (4 bytes) + avro_payload. Consumer looks up the schema by ID at read time — no inline schema in the message, no drift between producer and consumer. confluent-kafka-python wraps this; the SerializingProducer auto-registers the schema on first send.

The 4-byte schema ID is the secret to Avro's evolution story. Producers fetch the ID once at startup (cached forever), then prepend it to every record. Consumers fetch the schema by ID on first read (cached forever) — if the producer is on v2 and the consumer is on v1, the consumer still decodes correctly because it gets the writer's schema (v2) by ID, then resolves it against its own reader's schema (v1) using Avro's resolution rules (drop unknown fields, fill defaults). This is why Avro is the wire format for every Kafka data platform: the schema registry decouples producer deploys from consumer deploys.

Schema Registry IS API versioning applied to data — same compatibility invariants govern Kafka Avro, gRPC Protobuf, dbt contracts, and REST API JSON Schema

Connected to: ADR-001 (platform architecture) →

Schema Registry is structurally API versioning applied to data. The same BACKWARD / FORWARD / FULL / BREAKING invariants that govern REST API evolution (gRPC Protobuf, OpenAPI, JSON Schema) govern Avro schema evolution on Kafka, dbt model contracts (since v1.5), and Great Expectations expectations. The pattern is invariant: every change is classified as compatible or breaking; compatible changes ship without coordination; breaking changes require blue-green or rollback. A Kafka Avro consumer, a gRPC client, a dbt model contract, and a REST API caller all benefit from the SAME compatibility checker math — the math says: BACKWARD if S_{n+1} ⊇ S_n (new reader reads old data), FORWARD if S_n ⊇ S_{n+1} (old reader reads new data), FULL if both, BREAKING if no valid transformation f exists. The only difference is the substrate (Kafka topic vs Protobuf descriptor vs dbt YAML vs OpenAPI spec) — the math is universal. Confluent Schema Registry, Apicurio Registry, AWS Glue Schema Registry, gRPC Protobuf, dbt contracts, and OpenAPI specs all converge on the same invariants because they're all solving the same problem: how to evolve a contract without breaking consumers.

Avro vs Protobuf vs JSON Schema — the same tradeoff at different layers

Connected to: ADR-050 (fold-section architecture) →

The three wire formats (Avro, Protobuf, JSON Schema) make the same tradeoff at different layers of the stack. Avro is schema-first + binary: the schema lives in the registry, the message carries only a 4-byte ID, the payload is compact binary. Protobuf is schema-first + tag-numbered: the schema is the .proto file, fields are numbered (adding a new field with a new tag is forward-compatible), the payload is binary but self-describing enough to skip unknown fields. JSON Schema is schema-optional + text: the schema is a validator, the message is human-readable JSON, types are weaker (no native int64, no required-by-default). The tradeoff: Avro is the most compact (best for Kafka data plane) but requires the registry at read time. Protobuf is moderately compact (best for gRPC microservices) and self-describing enough that schema mismatches don't break decoding. JSON Schema is the most flexible (best for REST APIs) but the most verbose. A Kafka engineer using Avro, a microservices engineer using Protobuf, and an API designer using JSON Schema all enforce the same BACKWARD/FORWARD/FULL/BREAKING invariants — only the wire format differs. The choice of wire format is a layer-of-the-stack decision: data plane (Avro), service plane (Protobuf), API plane (JSON Schema). Schema Registry applies the same compatibility math to all three.
