Automatic Clustering vs Liquid Clustering — same math
Snowflake Automatic Clustering and Databricks Liquid Clustering (card 41) are the SAME algorithm: continuous, targeted, incremental re-cluster of hot partitions. The math is identical (WAF O(1) per insert). The unit differs: micro-partition (~16MB) vs Parquet file (~1GB).

Why the convergence? Both Snowflake and Databricks independently arrived at the same algorithm because the math IS the answer. Reactive batch-OPTIMIZE (ZORDER) requires full-table rewrites — O(N) write amplification per OPTIMIZE call. The math demands an incremental, targeted solution: identify degraded units (hot partitions) and recluster only those. The 2024+ lakehouse landscape has converged on this algorithm. The choice of unit (micro-partition vs Parquet file) is a productization decision; the math is invariant.

Search Optimization Service — Bloom + min/max pruning
SOS combines two algorithms: Bloom filters (card 46) per micro-partition + free min/max stats. Point lookups check each micro-partition's [min, max] range first (cheap), then Bloom filter (still cheap), then row scan (expensive). Result: ~100x skip-ahead for absent values.

Two-layer pruning: (1) min/max stats are free on every micro-partition (built automatically during insert), so the engine skips partitions whose range doesn't contain the target value — for high-cardinality columns this prunes ~50-80% of partitions. (2) When SEARCH OPTIMIZATION is enabled, Snowflake additionally builds a Bloom filter per micro-partition — for the remaining ~20-50% of partitions, the Bloom filter further prunes ~95% with no row reads. Combined: ~99%+ skip-ahead on point lookups for high-cardinality columns (UUIDs, hash keys).

Databricks comparison: Delta Lake Bloom Filter Index (card 46) builds a Bloom filter per Parquet file (~1GB, ~10M rows). Snowflake SOS builds per micro-partition (~16MB, ~50K rows) — 60× more granular. Better for small-table point lookups (more partitions to skip), worse on storage overhead (more Bloom filters to maintain). Same algorithm, different granularity tradeoff.

9class MicroPartition:

11    def __init__(self, pid, rows):
12        self.pid = pid
13        self.rows = rows
14        # Min/max stats (free, automatic on every micro-partition)
15        self.min_uid = min(r[0] for r in rows)
16        self.max_uid = max(r[0] for r in rows)
17        # Bloom filter (only built if SEARCH OPTIMIZATION is enabled)
18        self.bloom = None  # built on demand
19 
20    def build_bloom(self, n_expected, fpr_target=0.01):
21        m = max(8, int(-n_expected * math.log(fpr_target) / (math.log(2) ** 2)))
22        k = max(1, int((m / n_expected) * math.log(2)))
23        self.bloom = {"m": m, "k": k, "bits": [False] * m, "size_bytes": (m + 7) // 8}
24        for r in self.rows:
25            self._bloom_add(r[0])
26 
27    def _bloom_add(self, x):
28        h1 = int(hashlib.md5(str(x).encode()).hexdigest(), 16)
29        h2 = int(hashlib.sha1(str(x).encode()).hexdigest(), 16)
30        for i in range(self.bloom["k"]):
31            self.bloom["bits"][(h1 + i * h2) % self.bloom["m"]] = True
32 
33    def maybe_contains(self, x):
34        if not self.bloom: return True  # no Bloom = no skip
35        h1 = int(hashlib.md5(str(x).encode()).hexdigest(), 16)
36        h2 = int(hashlib.sha1(str(x).encode()).hexdigest(), 16)
37        return all(self.bloom["bits"][(h1 + i * h2) % self.bloom["m"]] for i in range(self.bloom["k"]))

Snowflake vs Databricks is the Oracle vs Teradata redux — both win, in different segments

Connected to: ADR-001 (platform architecture) →

Snowflake (closed-source, BI-focused, serverless-first) is the Teradata of the 2020s — wins enterprise analytics. Databricks (closed-source, full-stack, ML-focused) is the Oracle of the 2020s — wins enterprise ML + lakehouse. Both are winning, in different segments. The 4 advanced primitives (incremental re-cluster, Bloom skip, OLTP+OLAP unification, BYO-ML) all have analogs in both vendors — same math, different productization. The cross-vendor comparison table IS the 20-year longevity artifact: when Snowflake gets acquired or Databricks pivots, we update a row; the table stands. The math is the anchor.

The same math, different unit — micro-partition vs Parquet file

Connected to: ADR-050 (fold-section architecture) →

Snowflake uses micro-partitions (~16MB compressed, ~50K rows) as the storage unit. Databricks uses Parquet files (~1GB, ~10M rows) — 60× larger. This choice ripples through every primitive: (1) Automatic Clustering re-clusters micro-partitions (finer-grained, faster recovery, more recluster work) vs Liquid Clustering re-clusters Parquet files (coarser, less recluster work per file). (2) SOS Bloom is per micro-partition (more granular skip-ahead for point lookups) vs Delta Bloom Index is per Parquet file (less granular, less storage overhead). (3) Hybrid Tables give OLTP+OLAP on micro-partitions (single platform) vs Lakebase is separate Postgres-on-S3 (separate platform). The math is identical; the unit is the productization choice. Snowflake's smaller unit = more granular control = better for small-to-medium workloads. Databricks' larger unit = less overhead = better for petabyte-scale.

Hybrid Tables IS Snowflake's bet against Lakebase — and the lakehouse fragmentation

Connected to: ADR-022 (pgvector for variant embeddings) →

Snowflake Hybrid Tables (UNISTORE) is the strategic counter-bet to Databricks Lakebase. Databricks said: 'OLTP requires a separate Postgres-on-S3 (Lakebase) — you can't unify OLTP+OLAP in one engine.' Snowflake said: 'Actually you can — micro-partitions are small enough (16MB) that row-level MVCC on them gives sub-10ms P99 point reads, while still supporting full-table OLAP scans.' Both are technically correct: Databricks' architecture (Parquet files 60× larger) literally cannot do sub-10ms point reads because the smallest unit is too big. Snowflake's architecture (micro-partitions) CAN, but at the cost of more metadata overhead. The choice is product strategy, not math. The math (B-tree, MVCC, micro-partition pruning) is universal. Snowflake bet on unification; Databricks bet on separation. Both will likely converge — Snowflake adds Lakebase-like OLTP outside Hybrid Tables, Databricks adds micro-partitions inside Delta. 5 years from now, the two will look more alike than different.

Automatic Clustering vs Liquid Clustering — same math
Snowflake Automatic Clustering and Databricks Liquid Clustering (card 41) are the SAME algorithm: continuous, targeted, incremental re-cluster of hot partitions. The math is identical (WAF O(1) per insert). The unit differs: micro-partition (~16MB) vs Parquet file (~1GB).

Why the convergence? Both Snowflake and Databricks independently arrived at the same algorithm because the math IS the answer. Reactive batch-OPTIMIZE (ZORDER) requires full-table rewrites — O(N) write amplification per OPTIMIZE call. The math demands an incremental, targeted solution: identify degraded units (hot partitions) and recluster only those. The 2024+ lakehouse landscape has converged on this algorithm. The choice of unit (micro-partition vs Parquet file) is a productization decision; the math is invariant.

11    def __init__(self, pid, rows):
12        self.pid = pid
13        self.rows = rows  # list of (user_id, ts)
14        self.min_uid = min(r[0] for r in rows)
15        self.max_uid = max(r[0] for r in rows)
16        self.min_ts = min(r[1] for r in rows)

19    def overlaps(self, other):
20        """Two partitions are 'interleaved' if their ranges overlap."""
21        return (self.min_uid <= other.max_uid and self.max_uid >= other.min_uid and
22                self.min_ts <= other.max_ts and self.max_ts >= other.min_ts)
23 
24    def cluster_quality(self):
25        """Quality = how tightly the partition's ranges cover its rows.
26        Quality 1 = perfect, 0 = random spread."""
27        uid_range = max(1, self.max_uid - self.min_uid)
28        ts_range = max(1, self.max_ts - self.min_ts)
29        return 1.0 / (1.0 + uid_range / 1000 + ts_range / 1000)

Search Optimization Service — Bloom + min/max pruning
SOS combines two algorithms: Bloom filters (card 46) per micro-partition + free min/max stats. Point lookups check each micro-partition's [min, max] range first (cheap), then Bloom filter (still cheap), then row scan (expensive). Result: ~100x skip-ahead for absent values.

Two-layer pruning: (1) min/max stats are free on every micro-partition (built automatically during insert), so the engine skips partitions whose range doesn't contain the target value — for high-cardinality columns this prunes ~50-80% of partitions. (2) When SEARCH OPTIMIZATION is enabled, Snowflake additionally builds a Bloom filter per micro-partition — for the remaining ~20-50% of partitions, the Bloom filter further prunes ~95% with no row reads. Combined: ~99%+ skip-ahead on point lookups for high-cardinality columns (UUIDs, hash keys).

Databricks comparison: Delta Lake Bloom Filter Index (card 46) builds a Bloom filter per Parquet file (~1GB, ~10M rows). Snowflake SOS builds per micro-partition (~16MB, ~50K rows) — 60× more granular. Better for small-table point lookups (more partitions to skip), worse on storage overhead (more Bloom filters to maintain). Same algorithm, different granularity tradeoff.

5import hashlib, math, random, json

7random.seed(42)

9class MicroPartition:
10    """Snowflake micro-partition with min/max + Bloom filter."""
11    def __init__(self, pid, rows):
12        self.pid = pid
13        self.rows = rows
14        # Min/max stats (free, automatic on every micro-partition)
15        self.min_uid = min(r[0] for r in rows)
16        self.max_uid = max(r[0] for r in rows)
17        # Bloom filter (only built if SEARCH OPTIMIZATION is enabled)
18        self.bloom = None  # built on demand
19 
20    def build_bloom(self, n_expected, fpr_target=0.01):
21        m = max(8, int(-n_expected * math.log(fpr_target) / (math.log(2) ** 2)))
22        k = max(1, int((m / n_expected) * math.log(2)))
23        self.bloom = {"m": m, "k": k, "bits": [False] * m, "size_bytes": (m + 7) // 8}
24        for r in self.rows:
25            self._bloom_add(r[0])
26 
27    def _bloom_add(self, x):
28        h1 = int(hashlib.md5(str(x).encode()).hexdigest(), 16)
29        h2 = int(hashlib.sha1(str(x).encode()).hexdigest(), 16)
30        for i in range(self.bloom["k"]):
31            self.bloom["bits"][(h1 + i * h2) % self.bloom["m"]] = True
32 
33    def maybe_contains(self, x):
34        if not self.bloom: return True  # no Bloom = no skip
35        h1 = int(hashlib.md5(str(x).encode()).hexdigest(), 16)
36        h2 = int(hashlib.sha1(str(x).encode()).hexdigest(), 16)
37        return all(self.bloom["bits"][(h1 + i * h2) % self.bloom["m"]] for i in range(self.bloom["k"]))
38 
39    def min_max_skip(self, target):
40        """Returns False if target can't possibly be in this partition (min/max pruning)."""
41        return self.min_uid <= target <= self.max_uid

The same math, different unit — micro-partition vs Parquet file

Connected to: ADR-050 (fold-section architecture) →

Snowflake uses micro-partitions (~16MB compressed, ~50K rows) as the storage unit. Databricks uses Parquet files (~1GB, ~10M rows) — 60× larger. This choice ripples through every primitive: (1) Automatic Clustering re-clusters micro-partitions (finer-grained, faster recovery, more recluster work) vs Liquid Clustering re-clusters Parquet files (coarser, less recluster work per file). (2) SOS Bloom is per micro-partition (more granular skip-ahead for point lookups) vs Delta Bloom Index is per Parquet file (less granular, less storage overhead). (3) Hybrid Tables give OLTP+OLAP on micro-partitions (single platform) vs Lakebase is separate Postgres-on-S3 (separate platform). The math is identical; the unit is the productization choice. Snowflake's smaller unit = more granular control = better for small-to-medium workloads. Databricks' larger unit = less overhead = better for petabyte-scale.

Hybrid Tables IS Snowflake's bet against Lakebase — and the lakehouse fragmentation

Connected to: ADR-022 (pgvector for variant embeddings) →

Snowflake Hybrid Tables (UNISTORE) is the strategic counter-bet to Databricks Lakebase. Databricks said: 'OLTP requires a separate Postgres-on-S3 (Lakebase) — you can't unify OLTP+OLAP in one engine.' Snowflake said: 'Actually you can — micro-partitions are small enough (16MB) that row-level MVCC on them gives sub-10ms P99 point reads, while still supporting full-table OLAP scans.' Both are technically correct: Databricks' architecture (Parquet files 60× larger) literally cannot do sub-10ms point reads because the smallest unit is too big. Snowflake's architecture (micro-partitions) CAN, but at the cost of more metadata overhead. The choice is product strategy, not math. The math (B-tree, MVCC, micro-partition pruning) is universal. Snowflake bet on unification; Databricks bet on separation. Both will likely converge — Snowflake adds Lakebase-like OLTP outside Hybrid Tables, Databricks adds micro-partitions inside Delta. 5 years from now, the two will look more alike than different.
